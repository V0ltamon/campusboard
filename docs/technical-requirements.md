# Технічне завдання — CampusBoard
Версія 1.0. Автор: Цуріков Данило Антонович, ПІ-423.
Тип: індивідуальний навчальний проєкт. Стан: вимоги до майбутнього MVP.

## 1. Назва та опис
CampusBoard — адаптивна дошка студентських оголошень. Користувачі
публікують пропозиції щодо речей, підручників, навчальної допомоги й подій,
а відвідувачі знаходять їх у каталозі. Сервіс не проводить оплату чи доставку.

## 2. Проблема
У чатах немає єдиного каталогу, структурованого пошуку й зрозумілого
статусу актуальності. Контакти та зміст змішуються з іншими повідомленнями;
скарги опрацьовуються несистемно. Проєкт забезпечує категорії, пошук,
керування оголошеннями та фіксацію рішень модерації.

## 3. Мета та аудиторія
Мета — створити MVP, у якому можна знайти оголошення, опублікувати власне,
закрити неактуальне й повідомити про порушення.
Аудиторія: студенти, які шукають або пропонують речі, допомогу та події.
Навчальний пілот не перевіряє належність до закладу освіти документами.

## 4. Ролі та права
| Роль | Доступ |
|---|---|
| Гість | Головна, каталог, публічні деталі без контактів, правила, вхід, реєстрація |
| Користувач | Усе для гостя, власний профіль, власні оголошення, обране, скарги й контакти авторів |
| Модератор | Усе для користувача, черга скарг і приховування оголошень із причиною; не змінює ролі |
| Адміністратор | Усе для модератора, категорії, ролі й блокування; не може позбавити систему останнього активного адміністратора |
Сервер перевіряє і роль, і належність ресурсу. Автор не редагує чуже
оголошення. Модератор не змінює авторський текст, а тільки його видимість.
Самореєстрація не дозволяє вибрати привілейовану роль. Перший адміністратор
створюється через окрему процедуру початкового налаштування.

| FR-08 | Деталі та контакти | Гість бачить опис без контакту; активний автентифікований користувач бачить контакт, добровільно вказаний автором |

| FR-11 | Модерація | Модератор перевіряє скаргу, відхиляє її або приховує active-оголошення; причина рішення обов'язкова; рішення зберігається |
| FR-12 | Адміністрування | Зміна ролі, блокування акаунта, створення/перейменування/деактивація категорій; пов'язані категорії не видаляються фізично |
| FR-13 | Журнал рішень | Зберігаються виконавець, об'єкт, дія, час і причина для модерації, ролей та блокувань |

### Життєвий цикл і дані
Оголошення: active → closed (автор), active → hidden (модератор/адміністратор).
У MVP чернеток і повторної публікації немає. Нове валідне оголошення одразу
active: використовується постмодерація. Публічний каталог показує тільки
active від неблокованих авторів. Closed/hidden доступні автору й персоналу;
сторонньому відвідувачу повертається 404.
Скарга: open → resolved (приховано) або rejected (відхилено), з причиною.
Повторне рішення по закритій скарзі відхиляється як конфлікт.
Блокування акаунта припиняє його сесії; активні оголошення автора не
показуються, поки акаунт заблокований. Акаунт і матеріали не видаляються.
Деактивована категорія лишається в існуючих оголошеннях і не доступна для нових.
Сутності: User, Listing, Category, Favorite, Report, AuditLog.
Ціна зберігається цілим числом копійок, час — UTC; відображення — локальне.

## 7. Обмеження проєкту
Один розробник. Перша версія українською, один навчальний пілот, ціни у гривнях.
Немає онлайн-оплати, доставки, внутрішнього чату, рейтингу, сповіщень,
геолокації, мобільного застосунку, OAuth та відновлення пароля через email.
Email-підтвердження не реалізується в MVP; для демонстрації використовуються
тестові акаунти. Промисловий запуск потребує додаткового опрацювання цих функцій.
Планові технології: React/TypeScript/Vite; Node.js/Express/TypeScript;
PostgreSQL/Prisma; Vitest/Playwright. Версії визначаються при старті реалізації.

## 8. Критерії готовності MVP
- Реалізовані FR-01…FR-13 та сторінки з розділу 9.
- Усі чотири сценарії UC-01…UC-04 відтворюються з очікуваним результатом.
- Перевірені серверні заборони: гість не публікує; user не модерує;
  автор не редагує чужий ресурс; moderator не змінює ролі.
- Пройдені перевірки валідації, зображень, сесій, конфлікту скарг і останнього адміністратора.
- Перевірені три ширини екрана, клавіатура та ціль NFR-04; немає блокувальних дефектів.
- У README є відтворювані команди запуску, конфігурація та тестові дані без секретів.
- Код перевірений, зміни збережені у Git; завершені картки відповідають фактичним результатам.
Це критерії майбутньої реалізації, а не твердження про вже готовий продукт.
